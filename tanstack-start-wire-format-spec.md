# Wire format reference

Read the tutorial first. This page is a compact reference for the HTTP layer.

## Purpose

TanStack Start server functions are called through HTTP endpoints generated by the framework.

The browser call may look like a TypeScript function call, but the network request still has method, path, headers, and serialized data.

## Common fingerprints

Look for these signs in traffic:

```http
X-Tsr-ServerFn: true
```

```http
x-tss-serialized: true
```

Server function paths commonly use:

```text
/_serverFn/<function-id>
```

The exact function identifier is generated by the build system.

## POST body shape

A POST server function request body is usually a Seroval request envelope.

At a high level:

```json
{
  "t": "<serialized root value>",
  "f": 63,
  "m": []
}
```

The `t` field contains the serialized value tree.

The `f` field is a feature mask used by the serializer.

The `m` field contains marked references when the serialized graph needs them.

## GET payload shape

A GET server function may place the serialized payload in the query string.

```text
/_serverFn/<function-id>?payload=<url-encoded-seroval-envelope>
```

For testing, decode the URL parameter before editing it. Re-encode it before sending.

## Response shape

Non-streaming responses are usually serialized JSON values.

Streaming responses may use:

```http
Content-Type: application/x-tss-framed; v=1
```

Treat framed responses as a transport format. Decode frames before deciding what the application returned.

## Security notes

Wire-format failures and application validation failures are different.

- Bad Seroval shape should fail during deserialization.
- Valid Seroval with unsafe application data should fail during validation.
- Valid data from an unauthorized user should fail during authorization.

Testing should record which stage failed.

# TanStack Start Wire Format Spec

> **Read this first** if you intercepted odd JSON on `/_serverFn/…` or saw `application/x-tss-framed`. The rest walks headers, envelopes, and response shapes top to bottom.

This guide explains the TanStack Start server function wire format from the point of view of a novice pentester using Burp, curl, or a small script.

TanStack Start is a full-stack framework built on TanStack Router. Its RPC feature is called a server function. A browser calls a server function by sending HTTP to a framework route such as `/_serverFn/<function-id>`.

The body is usually not normal application JSON. TanStack Start serializes values with Seroval, a JavaScript value serializer. Seroval can represent values that plain JSON cannot, such as `undefined`, `Date`, `Map`, `Set`, cycles, shared references, `Error`, and streams.

## What To Look For

TanStack Start server function traffic often has these headers:

```http
X-Tsr-ServerFn: true
Accept: application/x-tss-framed, application/x-ndjson, application/json
```

Responses serialized by TanStack Start include:

```http
x-tss-serialized: true
```

If the response streams data, the content type is:

```http
Content-Type: application/x-tss-framed; v=1
```

If the response is not streaming, the content type is usually:

```http
Content-Type: application/json
```

The default server function URL base is:

```text
/_serverFn/
```

In the sampled app, the client bundle defines server functions like this:

```js
function wt(id) {
  const url = "/_serverFn/" + id
  return (...args) => serverFnFetcher(url, args, fetch)
}
```

Function IDs are usually embedded in client JavaScript as 64-character hex strings:

```js
createServerFn({ method: "POST" }).handler(createClientRpc("9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"))
```

## Server Function Request Shape

A minimal JSON `POST` request looks like this:

```http
POST /_serverFn/<function-id> HTTP/1.1
Host: target.example
X-Tsr-ServerFn: true
Accept: application/x-tss-framed, application/x-ndjson, application/json
Content-Type: application/json

{"t":{"t":10,"i":0,"p":{"k":["data"],"v":[{"t":10,"i":1,"p":{"k":["x"],"v":[{"t":0,"s":1}]},"o":0}]},"o":0},"f":63,"m":[]}
```

That body means:

```json
{
  "data": {
    "x": 1
  }
}
```

For `POST`, the JSON request body is a Seroval wrapper:

```json
{
  "t": "<root Seroval node>",
  "f": 63,
  "m": []
}
```

Fields:

| Field | Meaning |
|---|---|
| `t` | Root Seroval node |
| `f` | Feature mask used by Seroval |
| `m` | Marked reference IDs used by Seroval vanilla JSON mode |

For `GET`, the same serialized JSON is placed in the query string under `payload`:

```http
GET /_serverFn/<function-id>?payload=<url-encoded-seroval-json> HTTP/1.1
Host: target.example
X-Tsr-ServerFn: true
Accept: application/x-tss-framed, application/x-ndjson, application/json
```

For `FormData`, the browser sends real multipart data. TanStack only serializes extra server function context into a field named:

```text
__TSS_CONTEXT
```

## Response Shape

A normal successful response is a bare Seroval cross-JSON node. It is not wrapped in `{ "t": ..., "f": ..., "m": ... }`.

Example response:

```json
{"t":10,"i":0,"p":{"k":["result","error","context"],"v":[{"t":2,"s":1},{"t":2,"s":1},{"t":11,"i":1,"p":{"k":[],"v":[]},"o":0}]},"o":0}
```

Decoded:

```json
{
  "result": undefined,
  "error": undefined,
  "context": {}
}
```

The important object keys are:

| Key | Meaning |
|---|---|
| `result` | Return value from the server function |
| `error` | Error thrown by the server function or middleware |
| `context` | Context sent back from middleware |

If `error` is not `undefined`, the client throws it.

## Seroval Node Basics

Every Seroval node has a type tag named `t`.

Common fields:

| Field | Meaning |
|---|---|
| `t` | Node type |
| `i` | Identity/reference ID for objects and containers |
| `s` | Scalar value, constant ID, or plugin data |
| `c` | Constructor name, RegExp source, or plugin tag |
| `m` | Error message or RegExp flags |
| `p` | Object properties |
| `e` | Map entries |
| `a` | Array items, Set items, or stream event fields |
| `f` | Nested node, fulfilled value, factory, or backing buffer |
| `b` | Byte offset |
| `l` | Length |
| `o` | Object flag |

Do not confuse the outer request wrapper field `t` with a node's inner `t`. A request body has an outer `t` that points to the root node.

## Primitive Values

Numbers are simple:

```json
{"t":0,"s":42}
```

Strings are simple:

```json
{"t":1,"s":"hello"}
```

BigInts are decimal strings:

```json
{"t":3,"s":"12345678901234567890"}
```

Constants use `t: 2`.

| Node | Decoded value |
|---|---|
| `{"t":2,"s":0}` | `null` |
| `{"t":2,"s":1}` | `undefined` |
| `{"t":2,"s":2}` | `true` |
| `{"t":2,"s":3}` | `false` |
| `{"t":2,"s":4}` | `-0` |
| `{"t":2,"s":5}` | `Infinity` |
| `{"t":2,"s":6}` | `-Infinity` |
| `{"t":2,"s":7}` | `NaN` |

## Containers

Objects use `t: 10`.

```json
{"t":10,"i":0,"p":{"k":["name"],"v":[{"t":1,"s":"alice"}]},"o":0}
```

Decoded:

```json
{"name":"alice"}
```

Null-prototype objects use `t: 11`. They have the same property shape as normal objects.

Arrays use `t: 9`.

```json
{"t":9,"i":0,"a":[{"t":0,"s":1},0,{"t":2,"s":1}],"o":0}
```

Decoded:

```js
[1, <empty slot>, undefined]
```

In arrays, literal `0` means an empty slot, not the number zero. The number zero is:

```json
{"t":0,"s":0}
```

Sets use `t: 7`.

```json
{"t":7,"i":0,"a":[{"t":0,"s":1},{"t":1,"s":"x"}]}
```

Decoded:

```js
new Set([1, "x"])
```

Maps use `t: 8`.

```json
{"t":8,"i":0,"e":{"k":[{"t":1,"s":"k"}],"v":[{"t":0,"s":2}]},"f":{"t":26,"i":1,"s":0}}
```

Decoded:

```js
new Map([["k", 2]])
```

## References And Cycles

The `i` field gives an object an identity. Later nodes can point back to that identity.

An indexed value reference uses `t: 4`:

```json
{"t":4,"i":0}
```

A self-referencing object looks like this:

```json
{"t":10,"i":0,"p":{"k":["self"],"v":[{"t":4,"i":0}]},"o":0}
```

Decoded:

```js
const obj = {}
obj.self = obj
```

When editing payloads by hand, keep reference IDs consistent. If you duplicate a referenced object and reuse the same `i`, you are creating shared identity, not a copy.

## Object Flags

The `o` field describes object mutability.

| `o` | Meaning |
|---:|---|
| `0` | Normal object |
| `1` | Non-extensible object |
| `2` | Sealed object |
| `3` | Frozen object |

For normal testing payloads, use `o: 0`.

## Dates And RegExp

Dates use `t: 5`.

```json
{"t":5,"i":0,"s":"2020-01-02T03:04:05.000Z"}
```

RegExp uses `t: 6`.

```json
{"t":6,"i":0,"c":"ab+","m":"gi"}
```

Decoded:

```js
/ab+/gi
```

## Binary And Typed Arrays

ArrayBuffers use base64:

```json
{"t":19,"i":0,"s":"AQID","f":{"t":26,"i":1,"s":5}}
```

Decoded bytes:

```text
01 02 03
```

Typed arrays point at an ArrayBuffer:

```json
{"t":15,"i":0,"c":"Uint8Array","f":{"t":19,"i":1,"s":"AQID","f":{"t":26,"i":2,"s":5}},"b":0,"l":3}
```

DataViews use `t: 20`:

```json
{"t":20,"i":0,"f":{"t":19,"i":1,"s":"AQIDBA==","f":{"t":26,"i":2,"s":5}},"b":1,"l":2}
```

## Errors

Plain Seroval errors use `t: 13`.

```json
{"t":13,"i":0,"s":0,"m":"boom","p":{"k":["stack"],"v":[{"t":1,"s":"Error: boom\n..."}]}}
```

Error constructor IDs:

| `s` | Constructor |
|---:|---|
| `0` | `Error` |
| `1` | `EvalError` |
| `2` | `RangeError` |
| `3` | `ReferenceError` |
| `4` | `SyntaxError` |
| `5` | `TypeError` |
| `6` | `URIError` |

TanStack Start installs a shallow error plugin. In normal Start RPC, errors usually serialize as plugin nodes that include only the message:

```json
{"t":25,"i":0,"s":{"message":{"t":1,"s":"boom"}},"c":"$TSR/Error"}
```

Decoded:

```js
new Error("boom")
```

If you see stack traces in serialized errors, either the plugin was not applied or the application returned an error-like object itself.

## Plugins

Plugin nodes use `t: 25`.

```json
{"t":25,"i":0,"s":{"message":{"t":1,"s":"boom"}},"c":"$TSR/Error"}
```

Fields:

| Field | Meaning |
|---|---|
| `c` | Plugin tag |
| `s` | Plugin-specific object whose values are Seroval nodes |
| `i` | Identity ID |

TanStack-related plugin tags found in the framework:

| Tag | Meaning |
|---|---|
| `$TSR/Error` | Shallow `Error` serializer |
| `tss/RawStream` | TanStack raw binary stream |
| `seroval/plugins/web/ReadableStream` | Generic web `ReadableStream` |
| `$TSR/t/$TSS/serverfn` | Serialized server function reference |
| `$TSR/t/<custom-key>` | App-defined serialization adapter |

Treat unknown plugin tags as important. They mean the app has custom serializer logic or uses a framework type you have not modeled yet.

## Framed Responses

`application/x-tss-framed; v=1` is a binary frame protocol. It is not plain NDJSON.

Each frame is:

```text
[type:1 byte][streamId:4 bytes big-endian][length:4 bytes big-endian][payload:length bytes]
```

Frame types:

| Type | Name | Meaning |
|---:|---|---|
| `0` | JSON | UTF-8 Seroval JSON chunk. `streamId` must be `0` |
| `1` | CHUNK | Raw bytes for a `RawStream`. `streamId` must be non-zero |
| `2` | END | End of a raw stream |
| `3` | ERROR | Raw stream error message |

A framed response can interleave JSON events and raw binary stream chunks. The JSON payloads are complete JSON strings. The client parses each JSON frame and feeds it to Seroval with shared references.

## Redirects And Raw Responses

Redirects from server functions are special. They are plain JSON, not Seroval:

```json
{"href":"/login","statusCode":302,"isSerializedRedirect":true}
```

If a server function returns a normal `Response` object, TanStack can pass it through with:

```http
x-tss-raw: true
```

When `x-tss-raw: true` is present, do not Seroval-decode the body.

## Editing Checklist

When editing a TanStack Start RPC request in Burp:

1. Confirm the URL starts with `/_serverFn/` or the configured server function base.
2. Confirm the request has `X-Tsr-ServerFn: true`.
3. Confirm whether the method should be `GET` or `POST`.
4. For `POST`, edit the Seroval wrapper body.
5. For `GET`, URL-decode the `payload` parameter, edit it, then URL-encode it again.
6. Preserve the outer `{ "t": ..., "f": ..., "m": ... }` wrapper for requests.
7. Preserve object reference IDs when editing cyclic or shared structures.
8. Use `{"t":2,"s":1}` for `undefined`; do not use JSON `null` unless you mean JavaScript `null`.
9. Use `o: 0` for normal objects unless specifically testing object flags.
10. Fix `Content-Length` after changing a request body.

## Security Notes

The framework does not enforce authorization for server functions. Authorization belongs in app middleware or user code.

`X-Tsr-ServerFn: true` is not a secret. It mainly changes framework response handling and causes browser CORS preflight because it is a non-simple header.

The framework filters some dangerous context keys with `safeObjectMerge`, including `__proto__`, `constructor`, and `prototype`. Seroval itself assigns dangerous object property names with `Object.defineProperty`, which avoids the classic `obj.__proto__ = value` setter path.

Malformed Seroval usually becomes a deserialization error. Useful probes include:

- Unknown `t` tag
- Bad reference ID
- Duplicate `i` ID
- Very deep object graph
- Oversized `GET` payload
- Unknown plugin tag
- Bad ArrayBuffer base64
- Mismatched typed array offset and length

`X-Powered-By: ASP.NET` is not emitted by the TanStack source reviewed here. If present, assume a reverse proxy or front-end platform is adding it. Test for proxy/parser issues separately from the TanStack RPC protocol.
